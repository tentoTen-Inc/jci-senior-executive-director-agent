## 1. 目的・スコープ

LINE に流れた**資料（PDF）とやり取り**を、ボットの回答の根拠に使えるようにし、回答の良し悪しを記録して改善に回す。

### きっかけ（2026-10-06）
専務が個別トークで「福島ブロックの年内スケジュール（PDF）」を送り、続けて「福島ブロックの予定を教えて」と聞いたが、
- 「予定」というキーワードで定型の「次回の予定」に回り、AI に届かなかった
- そもそも AI は Firestore（自LOMのイベント・対外連絡）しか見ておらず、LINE で共有された PDF を知らない

### やること
| # | 内容 | フェーズ |
|---|---|---|
| 1 | **ナレッジ索引**: PDF の本文とテキストメッセージを分割・ベクトル化して BigQuery に蓄積（毎時） | P6-4a |
| 2 | **検索して答える（RAG）**: 質問に近い資料・発言を探し、既存の回答材料に足して Gemini が答える。**出典を明示** | P6-4a |
| 3 | **見られる範囲の制御**: 質問者が見られるもの（自分の個別トーク・自分が発言したことのあるグループ）だけを検索 | P6-4a |
| 4 | **振り分けの見直し**: 長い自由文はキーワードの定型応答ではなく AI へ | P6-4a |
| 5 | **回答の記録と評価**: 質問・回答・使った出典・👍👎 を記録し、管理画面で振り返り、評価データとして出力 | P6-4b |

## 2. 構成

```
（毎時 tick）                       （質問が来たとき）
v_files（PDF本文）─┐                 質問 ──► ML.GENERATE_EMBEDDING（RETRIEVAL_QUERY）
v_messages_for_ai ─┼► 分割 ─► ML.GENERATE_EMBEDDING            │
（20字以上の発言）  ┘        （RETRIEVAL_DOCUMENT）            ▼
                                   │     見られる範囲に絞った knowledge_chunks を ML.DISTANCE で順位付け
                                   ▼                           │ 上位5件・距離のしきい値
                     line_lake.knowledge_chunks ◄──────────────┘
                                                               ▼
                         既存の回答材料（イベント・対外連絡）＋ 関連資料・発言（出典番号付き）→ Gemini → 回答
                                                               ▼
                                     ai_answer イベント（質問・回答・出典・根拠の有無）→ BigQuery
                                     👍/👎 → ai_feedback イベント → v_ai_answers → 管理画面「AI応答の振り返り」
```

- **ベクトル化も検索も BigQuery の中で完結**（BigQuery ML のリモートモデル経由で Vertex AI を呼ぶ）。アプリは SQL を1本投げるだけで、新しいライブラリやベクトルDBは不要。
- モデル: **`gemini-embedding-001`**（多言語・日本語に強い）、768次元。
- 検索は「見られる範囲で絞り込み → `ML.DISTANCE`（コサイン）で順位付け」の総当たり。`VECTOR_SEARCH` は
  絞り込み付きサブクエリを入力に取れないことを BigQuery 上で確認したため、範囲制御を確実にするこの形にした。
  件数が数十万を超えたら、範囲の判定を別クエリにして `VECTOR_SEARCH`＋ベクトル索引に切り替える。

## 3. ナレッジ索引（P6-4a）

### 3.1 `line_lake.knowledge_chunks`
| 列 | 型 | 内容 |
|---|---|---|
| `chunk_id` | STRING | `{source_kind}:{source_id}:{n}`（一意・冪等） |
| `source_kind` | STRING | `file` / `message` |
| `source_id` | STRING | LINE のメッセージID |
| `chunk_no` | INT64 | 何番目の断片か |
| `scope_type` | STRING | `group` / `room` / `user`（どこで共有されたか） |
| `scope_id` | STRING | グループID・複数人トークID・個別トークならユーザーID |
| `user_id` | STRING | 送信者 |
| `sent_at` | TIMESTAMP | 送信時刻 |
| `title` | STRING | ファイル名（メッセージは null） |
| `content` | STRING | 断片の本文（先頭に「資料『…』(日付)」等の見出しを付けてベクトル化の精度を上げる） |
| `embedding` | ARRAY<FLOAT64> | 768次元 |
| `indexed_at` | TIMESTAMP | 索引した時刻 |

### 3.2 毎時の索引ジョブ（tick に相乗り）
1. **追加**: 未索引の断片を作り、`ML.GENERATE_EMBEDDING` でベクトル化して INSERT（1回あたり最大500断片。失敗した断片は入れず次回再試行）
   - PDF: 本文を 800 字ごと・100 字重ねて分割
   - メッセージ: **20字以上**のテキストのみ（挨拶やスタンプは保存はするが検索対象にしない）
2. **削除**: 送信取消されたメッセージ・ファイルの断片を DELETE（プライバシー方針どおり）

## 4. 検索して答える（P6-4a）

### 4.1 見られる範囲（最重要）
検索は**質問者が元々見られる情報だけ**に絞る。グループの会話を、そのグループにいない人へ漏らさない。

| 断片の共有場所 | 検索してよい人 |
|---|---|
| 個別トーク | そのトークの本人だけ |
| グループ・複数人トーク | そのグループで**発言したことがある人**（LINE の通常アカウントではグループのメンバー一覧を取得できないため、発言履歴で判定する安全側の近似） |

- 役職による特別扱いはしない（専務もルールは同じ）。全グループの閲覧は管理画面（IAP）で行う。
- 他会員の個人情報を答えない既存のルール（F8-4）はそのまま。

### 4.2 回答への組み込み
- 関連度（コサイン距離）がしきい値以下の上位5件を「# LINEで共有された資料・やり取り」として回答材料に追加。各件に `[1]` のような出典番号と、資料名・日付・共有場所（個別／グループ名）を付ける。
- プロンプトに「LINE由来の情報を使ったら出典番号を書く」「資料の内容は会議資料であり確定情報とは限らない旨を必要に応じて添える」を追加。
- 検索が失敗・未設定でも、従来の材料だけで回答する（4.4）。

### 4.3 振り分けの見直し
キーワードによる定型応答（次回の予定・自分の出欠状況・事務局連絡）は、**メニューのボタンか12字以下の短い文**のときだけにする。
それより長い自由文は AI に回す（AI は従来どおりイベント情報も材料に持つので「次の例会はいつ？」にも答えられる）。
出欠の自然文回答（F4-7）の経路は変えない。

### 4.4 設定と無効化
- 環境変数 `LAKE_EMBEDDING_MODEL`（例 `line_lake.embedding_model`）が無ければ索引も検索もしない（従来どおり）。
- BigQuery の呼び出しは1回（ベクトル化＋検索を1本の SQL で）。目安 2〜4 秒。

## 5. 回答の記録と評価（P6-4b）

| 記録 | 内容 |
|---|---|
| `ai_answer` イベント | 回答ID・質問・回答・使った出典（chunk_id・距離）・根拠の有無・取次の有無・モデル・トークン数 |
| `ai_feedback` イベント | 回答ID・👍/👎・押した人 |

- AI の回答には「👍 役に立った / 👎 違う」のクイックリプライを付ける（押すと短いお礼を返す）。
- ビュー `v_ai_answers`: 回答ごとに最新の評価を付けたもの（評価データの元）。
- 管理画面「AI応答の振り返り」: 一覧（👎・根拠なしで絞り込み）、出典の確認、**評価データの CSV 出力**（プロンプト改善や将来のモデル評価に使う）。

## 6. 権限・コスト

| 主体 | 追加の権限 |
|---|---|
| BigQuery 接続（`vertex-ai`）の SA | Vertex AI ユーザー（埋め込みモデルの呼び出し） |
| `app-runtime` | 接続の利用（`bigquery.connectionUser`）、`line_lake` の編集（索引の追加・削除） |

コスト: ベクトル化は1文字あたりごく小額（想定規模で月数円〜数十円）。検索は数百件〜数万件の総当たりで BigQuery の無料枠内。
