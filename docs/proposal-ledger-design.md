# 議案台帳と作業文書の同期 詳細設計 v1.0（段階1）

最終更新: 2026-10-24（v1.1: 議案の作成は LOM 公式アカウントで行う）
前提: 要件 `docs/requirements.md` F6（議案の提出・形式チェック・レビュー・会議パッケージ）、
委員会資料の編集 `docs/committee-docs-edit-design.md`（表の「項目名｜内容」の読み書き）、
ドライブの資料のナレッジ `docs/drive-knowledge-design.md`

## 1. 目的と方針
これから議案が次々と提出される。議案に関わるデータ（事業名・実施日・場所・目的・審議の記録など）を
**台帳（Firestore）に構造化して正本とし、人が書く場所は今どおり Google ドキュメント**にする（2026-10-24 専務承認）。

```
委員長・副委員長 ──書く・コメント──► 事業計画書（Google ドキュメント：作業文書）
専務AI（LINE）   ──案→確認→書く──►        │
                                            │ 更新を検知して読み取る（表の項目名｜内容）
                                            ▼
                                 議案台帳（Firestore：正本）
                                 ├ 管理画面（一覧・提出状況・締切）
                                 ├ 形式チェック・AIレビュー（F6-4/F6-5）
                                 └ 段階2: 確定版（PDF＋台帳のコピー）・アジェンダ・会議パッケージを自動作成
```

- 台帳は文書から作る（文書 → 台帳の一方向）。台帳の値を人が直接書き換える画面は作らない（二重管理を避ける）。
  例外は文書に無い管理情報（上程先の会議・状態・締切・専務確認）で、これは台帳だけが持つ。
- 版を V1・V2 とファイルで分けない。1つの文書の版の履歴で管理し、確定は段階2の「確定版」で行う。

## 2. 事業計画書の構造（2027年度様式）
テンプレート: `06-各種フォーマット/01-議案書/【事業計画書書式】2027年度様式（フォーマット）`

| 区分 | 文書の形 | 台帳の項目 |
|---|---|---|
| 事業名 | 2列の表（1行） | `title` |
| 基本情報 | 4列の表「◯項目｜値｜◯項目｜値」 | `basics`: ファイル名・委員会名・職務分掌・担当副理事長・委員長・文書作成人・文書作成日時・担当役員確認日・専務理事確認日 |
| 事業要項 1〜15 | 2列の表。左の見出しは複数行を結合し、右に「■問題」「■問題の原因」などの小見出しの行と内容の行が交互に並ぶ | `sections`: 「1.事業実施に至る背景」「1.事業実施に至る背景・問題」… |
| 審議対象資料 | 4列の表「審議対象資料(★)｜予算書｜参考資料(☆)｜…」 | `basics` に含める |
| 審議の記録 | 見出し「【五役会議①】開催日：…」＋3列の表「意見/対応｜質問者/回答者｜内容」 | `feedback`: 会議ごとの意見と対応の一覧 |

台帳から使う主な値（読み取った項目から決める）:
- `event_date`: 「4.実施日と実施前後のスケジュール」の ■実施日（「2027年3月23日(火)」等を読み取る。読めなければ空）
- `venue`: 「5.実施場所」の1行目
- `participants`: 「10.対象者及び参加員数」

## 3. 文書の読み取りの拡張（`committee_docs.extract_fields`）
今の読み取りは「2列の表」と「見出し行のある表」だけ。事業計画書に合わせて次を足す（サマリーの読み取りは変えない）。

1. **結合された見出しの続きの行**: 左のセルが空の行は、直前の見出しの続きとして扱う。
2. **■小見出し**: 右のセルが「■〇〇」だけの行は小見出しとし、次の行の内容を「見出し・〇〇」の項目にする
   （例: `1.事業実施に至る背景・問題の原因`）。小見出しと内容が同じセルにある場合（6.事業内容の「■事業概要」等）は1つの項目のまま。
3. **4列の項目表**: 「◯」で始まるセルを項目名、その右のセルを値として読む（`◯担当副理事長` → `担当副理事長`）。
4. **審議の記録の表**: 直前の段落（「【五役会議①】開催日：2027年1月10日」）を表の名前にし、
   項目名を `五役会議①・意見1・内容` のようにする（今は同じ名前に (2)(3) と番号が付き、どの会議か分からない）。

これらは資料の編集（LINE で「事業計画書の目的を直して」）でもそのまま使える。

## 4. 台帳（`Proposal` の拡張）
既存の `Proposal`（状態・締切・形式チェック・AIレビュー・専務確認）に次を足す。

| 項目 | 内容 |
|---|---|
| `fiscal_year` | 年度（2027） |
| `doc_id` | 作業文書（事業計画書）の Google ドキュメントID。`storage_uri` は互換のため残す |
| `doc_revision` / `synced_at` | 最後に読み取った版と日時 |
| `basics` | 基本情報（§2） |
| `sections` | 事業要項の各項目（項目名 → 内容） |
| `feedback` | 審議の記録 `[{meeting, kind: 意見/対応, no, person, text}]` |
| `event_date` / `venue` / `participants` | §2 の読み取り結果 |

`content`（全文）は形式チェック・AIレビューのために引き続き持つ（文書のテキスト全体）。

## 5. 同期
- 対象: `COMMITTEE_DOCS_FOLDER`（04-委員会）の各委員会フォルダの `01-例会・事業` 配下で、名前が「【計画書】」で始まる Google ドキュメント。
- tick（毎時）で、更新日時が変わった文書だけ読み取り、`doc_id` で台帳と突き合わせる（無ければ新規の議案として `entry` で作る）。
  1回あたりの件数と時間に上限を設ける（ドライブの取込と同じく 20 件・30 秒）。
- 文書がゴミ箱に入った・見つからない議案は `status=closed` にする（台帳は消さない）。
- 読み取りは `doc-editor`（04-委員会 のみ共有）を使う。

## 6. LINE で議案を作る
理事メンバーが「3月例会の事業計画書を作って」と送ると:
1. 委員会を決める（資料の編集と同じ: 名指し → 所属・担当 → 1つ）。
2. 年間スケジュール（`Event`）から該当する例会・事業を探し、日付を決める（見つからなければ聞き返す）。
3. 確認メッセージ「総務委員会の 2703_3月例会 の事業計画書を作ります。よろしいですか？［作成する］［やめる］」
4. ［作成する］で:
   - `01-例会・事業/2703_3月例会/` フォルダを作り（命名規則: `YYMM_名前`）、テンプレートをコピーして
     `【計画書】3月例会事業計画書` と名付ける
   - 基本情報（ファイル名・委員会名・職務分掌・担当副理事長・委員長・文書作成人・作成日時）を台帳と組織図から記入
   - テンプレートの古い年度表記（「2026年度様式」「2026年◯月」）を 2027 に直す
   - 議案を台帳に `entry` で登録し、`event_id` を結ぶ
   - 「作成しました」＋リンク。続けて「〇〇な例会にしたいので背景と目的を書いて」と頼めば資料の編集で埋められる
- **作成は LOM 公式アカウント（inawashiro.jc）で行う。** サービスアカウント（doc-editor）は Google の仕様で
  マイドライブにファイルを持てず、フォルダの作成やテンプレートのコピーができないため。
  LOM 公式 Gmail の OAuth（対外連絡の取込で使っている refresh token）に `drive` スコープを足して使う
  （`scripts/gmail_oauth_setup.py --with-drive` で一度だけ同意し直す）。作ったものは LOM のものとして年度をまたいで残る。
- 作った文書は 04-委員会 の中にあるので、記入（基本情報・年度表記）はこれまでどおり doc-editor で行う。
- テンプレートの文書IDは環境変数 `PLAN_TEMPLATE_DOC` で指定する。

## 7. 管理画面
議案の画面に、台帳の内容（基本情報・事業要項・審議の記録・実施日・場所）と作業文書へのリンク、最後に同期した日時を出す。
カンバン・提出マトリクス・形式チェック・AIレビューは今のまま（入力が構造化された分、形式チェックは項目ごとの空欄判定に置き換えられる）。

| フェーズ | 内容 |

## 9. テスト
- 読み取り: 2027年度様式の事業計画書の構造（Docs API の応答を軽くしたもの）で、■小見出し・4列の項目表・会議ごとの審議の記録が取れること。サマリーの結果が変わらないこと。
- 同期: 更新日時が変わった文書だけ読む・新規作成・ゴミ箱で closed・上限で次回へ。
- 作成: 権限・委員会の決め方・例会が見つからないとき・確認（本人のみ・期限・二重押し）・フォルダとファイルの命名・基本情報の記入。

## 10. 委員会サマリーと［提出する］（2026-10-27 専務承認・A案）
次の五役会（第2回五役予定者会議・日程調整中）に、各委員会が「委員会サマリー（年間計画）」を提出する。

| 段階 | いつ | どうやって |
|---|---|---|
| エントリー | サマリーが委員会フォルダにあれば | 同期（tick）で台帳に載る。提出締切・上程先は `scripts/set_summary_deadline.py` で設定 |
| 資料提出 | 副理事長・委員長が仕上げたとき | LIFF「委員会の議案」の［提出する］（確認つき） |
| 締切時 | 提出締切を過ぎた最初の tick | 専務に記入状況（提出済み／未提出・空欄の欄の数）を LINE で1回 |

### 10.1 同期（`proposal_sync`）
- 事業計画書（「【計画書】」で始まる）に加えて、委員会サマリー（`00-年間計画（サマリー）` 配下、または名前に summary／サマリー を含む Google ドキュメント。`doc_edit_intent.is_summary`）を
  `doc_type="年間計画（サマリー）"` で台帳に載せる。タイトルは「2027年度 〇〇委員会 年間計画（サマリー）」（年度は `Settings.operation_start`）。
- 記入欄（スローガン・現状分析・目指すべき状態・事業概要・事業手法・例会/事業・1〜12月）を `sections` に写す。「（参考）LOM日程」は写さない。
- 文書が見つからなくなった議案を閉じる処理は、計画書とサマリーの両方を「ある文書」として扱うので、サマリーを誤って閉じない。
- 空欄の欄の数（`blank_count`）: `sections` のうち空欄・記入例「◯」のままの欄。

### 10.2 ［提出する］／［提出を取り消す］（LIFF「委員会の議案」）
- 押せる人: その委員会の資料を更新できる理事メンバー（`committee_docs.can_edit`: 理事長・専務理事・担当副理事長・委員長）。事務局は見るだけ。
- ［提出する］: エントリー → 資料提出（確認つき）。履歴に `by="LINE: 氏名"`。専務理事に
  「【提出】〇〇委員会 年間計画（サマリー）が提出されました（氏名さん）」・空欄の欄の数・議案書リンクを LINE で知らせる。
  静音時間は送らず、明けた tick で送る（送る前に取り消されたら送らない）。管理画面で段階を変えたときは知らせない。
- ［提出を取り消す］: 資料提出 → エントリー（同じ権限・確認つき）。知らせはしない。
- チャットの自由文では提出しない（ボタンからだけ）。管理画面の議案ページの段階にもそのまま出る。

### 10.3 提出締切の記入状況
- 提出締切（`deadlines.submit`）を過ぎた最初の tick（静音時間を除く）で、締切を過ぎた議案を上程先の会議ごとにまとめ、
  各議案の段階（提出済み／未提出）・空欄の欄の数・議案書リンクを専務に1通で知らせる。
- 送った知らせは `Proposal.notices`（`"deadline:<締切>"`・`"submitted:<提出の時刻>"` → 送った時刻）に残し、同じ締切では二度送らない（締切を変えたら新しい締切でまた1回）。
- 締切から3日を過ぎたものは送らない（古い締切で一斉に送らないため）。

### 10.4 上程先が日程調整中のとき
- `Proposal.meeting_poll_id` に上程先の会議の日程調整を持つ。表示は、決まっていなければ「第2回五役予定者会議（日程調整中）」、
  決まれば（`poll.event_id`）その会議の名前と日時。`event_id` があればそちらを優先。
- 管理画面・LIFF の議案に「上程先」として出す（API が `meeting_label` を添える）。

### 10.5 テスト
`tests/test_proposal_sync.py`（サマリーの同期・閉じない・空欄）、`tests/test_proposal_submit.py`（権限・提出と取り消し・夜間・締切の知らせ・上程先・設定用スクリプト）。
