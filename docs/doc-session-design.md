# チャットは検索のみ・書き込みはボタンから（資料の作業セッション） 詳細設計 v1.0

最終更新: 2026-10-25
前提: 委員会資料の編集 `docs/committee-docs-edit-design.md`、議案台帳 `docs/proposal-ledger-design.md`、
予定の自然文操作 `docs/calendar-design.md` §5.2、出欠の自然文 F4-7

## 1. 原則（2026-10-25 専務の指示）
**リッチメニューのボタンなどで明示的に作業を始めない限り、LINE のチャットは検索・回答のみとし、
資料の更新・データの更新は一切行わない。**

背景: 単語での判定（「書いて」「サマリー」等）で資料の更新を受け付けていたところ、4月例会の議案書の話の続きで
サマリーが更新される、依頼が質問として扱われる、などの誤判定が起きた（2026-10-24。単語での判定は #160 で停止済み）。

- 自由文は、質問として答える（ナレッジ検索・自LOM情報）。書き込みはしない。
- 自由文が書き込みの依頼に見えるときは、その作業を始めるボタンを返すだけにする（押すのは本人）。
- 書き込みは、ボタン（postback）で始めた流れの中だけで行う。その中でも書き込み前の確認は必ず残す。

## 2. 今の書き込みの入口と、変更後
| 入口 | 今 | 変更後 |
|---|---|---|
| 資料の更新（自由文） | 単語で判定（停止中） | **作業セッション**（§4）の中だけ |
| 議案（事業計画書）の作成（自由文「〇月例会の計画書を作って」） | 確認後に作成 | 作業セッションの入口（［＋新しい事業計画書］）から。自由文には入口のボタンを返す |
| 予定の登録・変更・中止（自由文、五役・事務局） | 確認後に反映 | リッチメニュー［予定を登録・変更］の後の1通だけを予定の指示として扱う（10分で失効）。自由文には入口のボタンを返す |
| 出欠の登録（自由文「来週の例会は欠席で」） | 確認後に登録 | 自由文には［出欠を回答］のボタン（今のリッチメニューと同じ出欠の案内）を返す |
| 事務局への連絡（短い文「連絡」） | すぐ連絡票を作成 | 意見箱の案内（ボタン付き）を返すだけ（`docs/feedback-box-design.md` §2。［事務局に連絡］は廃止） |
| 答えられない質問の取次ぎ | すぐ取次ぎを記録 | 回答に［意見箱に送る］のボタンを付け、押したときだけ意見箱に保存（`docs/feedback-box-design.md` §3） |
| 出欠ボタン・日程調整・LINE 連携・AI 回答の👍👎 | ボタン | 変更なし（もともとボタン起点） |

会話の記憶・AI の回答の記録・受信メッセージのデータレイクへの保存は、書き込みではなく記録として今どおり行う。

## 3. リッチメニュー
> **この節は `docs/liff-menu-design.md`（2026-10-25 承認）に置き換わりました。** 以下は当初の案です。

立場ごとに別のメニューを結びつける（LINE の per-user rich menu）。組織図の取込・LINE 連携の承認のときに自動で付け替える。

| メニュー | 対象 | ボタン |
|---|---|---|
| 会員用（今のまま 2×2） | 下記以外 | 出欠を回答／次回の予定／自分の出欠状況／事務局に連絡 |
| 理事用（2×3） | 委員長・副理事長・直前理事長 | 上の4つ＋**資料を作る・直す**＋使い方 |
| 五役用（2×3） | 理事長・副理事長・専務理事・監事・事務局 | 上の4つ＋**資料を作る・直す**＋**予定を登録・変更** |

（副理事長は五役用。監事・事務局は資料の更新権限が無いので［資料を作る・直す］を押しても「対象の資料がありません」となる）

## 4. 資料の作業セッション
Claude との会話のセッションに近い。違いは **1つのセッションが1つの資料に結びつく** こと。

### 4.1 流れ
```
［資料を作る・直す］
  └「どの資料ですか？」 本人が更新できる資料をボタンで（最近更新された順・最大12件）
       ［4月例会 事業計画書］［組織未来推進委員会 サマリー］…［＋新しい事業計画書］
       └ 選ぶ → セッション開始。「📝 4月例会 事業計画書 の作業を始めます。直したい内容を送ってください」
  作業中の返信の先頭には毎回「📝 編集中：4月例会 事業計画書」。クイックリプライ［作業を終える］［別の資料］
  本人の文 → AI が「書き換えの案」「聞き返し」「質問への回答」のどれかを返す
       書き換えの案 →「次の3欄を書き込みます」＋［書き込む］［やめる］（先頭に資料名）
  ［書き込む］→ 版を確認して書き込み → 変更前の内容を記録 →「書き込みました」＋［さっきの変更を戻す］
  ［作業を終える］・30分操作なし・別の資料を選ぶ → 終了 → 質問モードへ
```
- ［＋新しい事業計画書］は、例会・事業を選ぶボタン → 確認 → 作成（`proposal_intent` の作成処理）→ そのままその資料のセッションを始める。
- セッション中の質問（「去年の4月例会はどんな内容？」）には、資料を変えずに答える（ナレッジ検索を使う）。

### 4.2 データ（Firestore）
| 保存場所 | 中身 |
|---|---|
| `chatStates/{member_id}` | `mode`（`question` / `doc` / `calendar`）・`session_id`・`expires_at`。文が届いたとき、質問か作業かをここだけで決める |
| `docSessions/{session_id}` | 本人・資料（ID・名前・委員会）・状態（`active` / `closed` / `expired`）・開始と最終操作の日時・終了の理由 |
| `docSessions/{id}/turns/{連番}` | 発言者（本人／AI）・本文・種類（指示／案／聞き返し／回答／書き込み）・時刻・関連する操作ID |
| `docSessions/{id}/edits/{op_id}` | 欄ごとの**変更前と変更後**・書き込み前後の版・状態（`proposed` / `applied` / `declined` / `expired` / `reverted`）・時刻 |

- `edits` は今の `pendingDocEdits` を置き換える（確認待ちの案と書き込みの記録を1か所に）。
- セッションの記録は終了後も残す（誰が何を頼み、AI が何を提案し、何が書き込まれたかを追えるように）。監査ログ `doc.edit` も今どおり。
- LINE のメッセージはデータレイク（BigQuery）にも今どおり残る。

### 4.3 1通ごとの処理
1. `chatStates` を見る。`doc` で期限内ならセッションの指示として扱う。それ以外は質問（書き込みなし）。
2. 資料を毎回読み直す（人がドキュメントを直接編集していても最新の内容を前提にする）。
3. AI（`doc_edit` タスク）に渡す: 資料の欄と今の内容、セッションの直近 10 往復、確認待ちの案（あれば）、ナレッジ検索の結果。
4. AI の出力: `kind`（`edit` / `ask` / `answer`）・`edits`・`message`。`edit` のときだけ確認ボタンを付ける。
5. ［書き込む］: 本人・期限・状態・権限を確認し、読んだ版から変わっていなければ書き込む。変更前の内容を `edits` に残す。
6. ［さっきの変更を戻す］: 直前の `applied` の変更前の内容で書き戻す（同じく版を確認し、確認ボタンを挟む）。

## 5. 予定の登録・変更（五役・事務局）
［予定を登録・変更］→「登録・変更したい予定を送ってください（例: 10/20 19時から理事会を登録）」→ `chatStates.mode=calendar`（10分）。
次の1通だけを `calendar_intent` で解釈し、今どおり確認してから反映する。終わったら質問モードに戻る。

## 6. フェーズ
| フェーズ | 内容 |
|---|---|
| S1 | 原則の適用: 自由文からの書き込み（議案作成・予定・出欠・連絡・取次ぎ）を止め、入口のボタンを返す。立場ごとのリッチメニュー。予定の登録・変更のモード（§5） |
| S2 | 資料の作業セッション（§4）: 資料の選択・会話・案・確認・書き込み・取り消し・終了。議案の作成をセッションの入口へ |

## 7. テスト
- 自由文では、どの立場・どの文でも書き込み（資料・議案・予定・出欠・連絡票・取次ぎ）が起きないこと（書き込み系の関数が呼ばれないことを確認するテスト）。
- 入口のボタンを返すこと、ボタンから始めた流れでは今どおり確認後に書き込めること。
- セッション: 開始・期限切れ・終了・別の資料への切り替え、作業中の文が質問扱いにならないこと、作業中でない文が書き込みにならないこと、取り消し、版の衝突。
